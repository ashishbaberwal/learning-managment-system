# ADR 0009: CI/CD — GitHub Actions, Schema Drift Gate, and Container Image Release

## Status
Accepted

## Context
Through Phases 0–9 every change was validated manually on the author's machine: `tsc`, `eslint`, a production build, and hand-run integration checks against live Redis/Postgres/Kafka. The repository has a GitHub remote but no automation, so nothing prevented a schema/migration drift, a type error, or a broken build from reaching `main`, and there was no deployable artifact — the app only ran via `pnpm dev` on the host.

## Decision
1. **Continuous integration (`.github/workflows/ci.yml`)** — on every PR and push to `main`, a `verify` job runs on Ubuntu with a `postgres:16-alpine` service container:
   - `pnpm install --frozen-lockfile` (root `postinstall` runs `prisma generate`)
   - `pnpm exec prisma migrate deploy` — proves all migrations apply cleanly to an empty database
   - `pnpm exec prisma migrate diff --from-schema-datasource --to-schema-datamodel --exit-code` — fails the build (exit 2) if the live schema does not exactly match `schema.prisma`, catching hand-edited migrations and forgotten `migrate dev` runs
   - `tsc --noEmit`, `eslint`, `next build`
   All secrets in CI are dummies: the build and typecheck never touch real services, so no repository secrets are required.
2. **Continuous delivery (`.github/workflows/release.yml`)** — every push to `main` builds the app image from the repo `Dockerfile` and pushes it to GHCR (`ghcr.io/<owner>/<repo>:latest` + `:sha`) with `GITHUB_TOKEN` and GitHub Actions layer cache. Deployment itself is out of scope: the image plus `docker-compose.yml` (infra) and the worker processes are the runtime contract.
3. **Production build = webpack, standalone output.** `package.json` build script changed from `next build --turbopack` to `next build`, and `next.config.ts` sets `output: "standalone"`. Turbopack builds failed page-data collection under standalone output (`PageNotFoundError` on nested dynamic admin routes); the webpack pipeline is the supported path for `output: standalone` in Next 15.5 and produces a traced, self-contained server. Dev still uses `next dev --turbopack`.
4. **Multi-stage Dockerfile** (`deps` → `builder` → `runner`): pnpm pinned to the repo's `packageManager` (`pnpm@11.10.0`), `openssl` installed for Prisma engines, dependency install with `--ignore-scripts` then an explicit `prisma generate` inside the builder, build-time dummy environment variables (identical in spirit to CI), and a slim runner that copies only `.next/standalone`, `.next/static`, and `public`. `.dockerignore` excludes `.env*`, `node_modules`, `.next`, `docs`, and `observability` so no secrets or junk enter the image.
5. **Toolchain pinned:** `.nvmrc` (`24`) drives `setup-node`, `packageManager` pins pnpm for both corepack-aware tooling and the Dockerfile, and `engines.node >= 20` documents the floor.

## Alternatives Considered
- **Turbopack production build with standalone output:** attempted first; fails today (`Failed to collect page data` / `PageNotFoundError` on `/admin/courses/[courseId]/[chapterId]/[lessonId]`). Kept Turbopack for dev only.
- **No-op CD / docs-only:** rejected; publishing to GHCR makes "deploy = run this image + infra" concrete and testable.
- **Deploy to a cloud host (Vercel/Fly):** no target exists — the architecture depends on the local compose stack (RabbitMQ, Kafka, Redis, exporters) and host-run workers; a single-host deployment via the same compose file is the natural next step when wanted.
- **Pushing images to Docker Hub:** GHCR needs no extra credentials (`GITHUB_TOKEN`) and keeps the artifact next to the source.
- **Making CI hit real Neon/Redis:** rejected; dummy env keeps CI hermetic, fast, and secret-free. Integration checks remain a documented manual step (and the migrations-on-empty-database test covers the riskiest DB path).

## Consequences
- **Positive:** Verified locally before merge: all 7 migrations apply cleanly to a fresh `postgres:16` with `No difference detected` on the drift check; the webpack standalone build passes and traces the Prisma engine + generated client; the built image (594 MB) runs and serves `/` (200, 0.8 s), `/courses` (200, 2.6 s against real Neon), and exposes `/api/metrics` — with Redis unreachable inside the container, reads still succeed via the Phase 7 fail-open path. `tsc`, `lint`, and the new build are green. Once pushed, `main` gets CI on every commit and an image per commit.
- **Negative / known caveats:** GHCR publishing starts only after the commits are pushed to `origin` (nothing is pushed automatically). `docker run --env-file` does not strip quotes from `.env` values — deployments must use unquoted env files or a secret manager (verified: quoted URLs fail env validation at container start). No automated tests exist yet, so CI validates compile/quality/migrations, not behavior; the image contains only the web app — workers and the compose stack are deployed separately. Turbopack production builds should be re-tried when the standalone incompatibility is fixed, to speed CI up.
